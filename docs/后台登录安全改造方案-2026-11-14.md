# 后台登录安全改造方案

日期：2026-11-14
范围：`/platform/admin/` 管理员登录（不涉及用户端与开放接口）
状态：**方案已定并已实现** —— P0 / P1 / P2（TOTP）/ L3 本轮落地，`tools/test-admin-security.js` **59 项**全绿；
短信与微信扫码列为后续阶段（等外部条件）。实现与本文有出入处以本文「实现口径」小节为准。

---

## 1. 目标与边界

原始诉求：「后台登录只有用户名密码不够安全，第一步加图形验证码，要挡住 AI 自动化」。

先纠一个前提：**图形验证码和滑块拼图都挡不住有准备的 AI**。它们能挡的是裸脚本 / 无脑 RPA，属于「摩擦层」。真正让自动化成本上升的是**服务端尝试次数上限 + 持有物第二因素**。所以本方案不把验证码当安全闸门，而是把它放在分层里的第二层。

目标拆解：

| 威胁 | 由哪层解决 |
|---|---|
| 自动化扫号 / 慢速撞库 | L0 服务端闸门 |
| 无脑脚本、重放、批量预求解 | L1 一次性挑战（验证码 + PoW） |
| 密码泄露、凭据填充、SIM/扫码之外的账号接管 | L2 TOTP 第二因素 |
| 令牌盗用、事后无感知 | L3 可撤销会话 + 审计告警 |
| 针对管理员本人的实时钓鱼 | **本方案不解决**（只有 Passkey/WebAuthn 抗钓鱼，列入远期） |

## 2. 现状盘点（核对源码，不是推测）

`server/routes/admin.js` 当前登录链路：

- **已有**：`login_attempts` 表 + 5 次 / 15 分钟失败锁定（只按 `username`）、初始随机密码写 `data/admin-init-password.txt`、弱口令标 `must_change_password`、生产环境受限令牌强制改密、统一报错「用户名或密码错误」。
- **已有但不完整**：`admin_logs` 表，但登录成败**不写进去**，后台看不到谁在撞。
- **缺口**：
  1. 锁定只按 username，换用户名 / 换出口 IP 即绕过；5 次/15 分钟 = 每账号 480 次/天，慢速撞库仍可行；
  2. `!admin || !verifyPassword(...)` 短路——用户名不存在时**不跑哈希**，响应时间差可枚举管理员账号；
  3. JWT `12h`、无 `jti` / 会话表 → 令牌被盗后**改密码也踢不掉**；
  4. 无图形验证码、无第二因素、无异动告警。

`sms_codes` / 微信扫码链路现状（与后续阶段相关）：

- `/api/portal/phone/code` **只把 6 位码写进 `sms_codes`，全仓无短信服务商调用**，devMode 时回明文 `devCode`；码明文入库、表里无 IP / created_at / 尝试次数；发码端点只要有个登录态账号就能无限调用（短信轰炸 + 烧钱）。**现在这条不是可用的短信通道**。
- `sms_codes` 校验侧有「5 次失败锁 10 分钟」内存计数，但只在绑定端点生效。
- 微信扫码：`wechat_sessions`（scene 300 秒 TTL）收到 SCAN 事件**直接置 `confirmed`**，无微信内二次确认；扫码后签发的是用户级 `handoff ticket`（`scope=user`），不是 `signAdmin`。
- `admins` 表**没有 phone，也没有微信 openid 字段**；现有扫码是「任何微信用户扫码 → 自动建普通用户」，**没有管理员白名单**。
- `/api/wechat/simulate/:scene` 模拟后门生产已硬禁，但接进后台登录前必须再确认它绝不能生成管理员会话。

## 3. 攻防调研结论（2025–2026 公开数据）

| 来源 | 结论 |
|---|---|
| USENIX Security 2025，Halligan（通用 VLM 求解器） | 26 类 / 2600 个视觉挑战解决率 **60.7%**；30 天野外未见题型 **70.6%**；单个中位成本 **2.4 美分 / 21.8 秒** |
| NeurIPS 2025，Open CaptchaWorld | 20 类验证码，人类 93.3%，最佳模型 o3 仅 40%；`Slide Puzzle` 属所有模型都未攻克的类型之一 |
| MCA-Bench 2025 | Qwen2.5-VL 在扭曲文字 / 九宫格高成功率，面对滑块、旋转明显下降 |
| 2024，行为验证型滑块 CAPTCHA 鲁棒性研究 | 针对 5 种主流滑块，攻击成功率 **87.5%~100%** |
| 2026-11 arXiv 预印本（四川大学） | YOLOv11 定位缺口 + GAN 学真人二维轨迹，攻破 Capy / 顶象 / 极验 / 数美 / 腾讯等 6 家，**>90%、约 5 秒** |
| Lattice 综述 | 现代行为栈（reCAPTCHA v3 / Turnstile）仍抵抗直接 LLM 攻击，撑住的是**风控大脑**不是谜题；AkiraBot 用 LLM + 打码服务刷了 8 万+ 站点 |

**两组数据不矛盾**：通用大模型「零准备」解滑块确实吃力，但攻击者针对一个**题型固定、可反复采样的登录页**可以离线定制求解器——后台登录正是这种靶子。

关键推论：滑块的价值在厂商的跨站设备指纹 / IP 声誉 / 历史会话，自研只能复刻 UI，拿不到风控大脑，甚至可能比字符验证码更弱（只校验最终 x 坐标时，AI 读图算坐标即可）。

**算得过来的账**：Halligan 是 2.4 美分/次。L0 把同一 IP / 账号的尝试压到每小时十几次，即使每次都破，攻击者也只有十几次机会——AI 的单次成功率再高也被总量限流消掉。

## 4. 选型判断

| 方案 | 抗 AI 自动化 | 抗实时钓鱼 | 抗账号接管 | 落地 | 结论 |
|---|---|---|---|---|---|
| 字符图形验证码 | 弱（摩擦层） | — | — | 快 | **做**，但只作 L1，条件触发 |
| 滑块拼图（自研） | 弱于预期，且成本高 | — | — | 重（图片素材 / 轨迹判别 / 移动端 / 无障碍） | **不做** |
| 第三方行为风控（极验 / Turnstile） | 强（买的是信誉库） | — | — | 联网 SDK、管理员登录数据外送、子路径与合规评估 | **不做**，与纯自托管形态冲突 |
| 手机短信 | 强（持有 SIM） | 弱 | 怕 SIM 补卡 / SS7 | 快，但**等短信账户审核** | 后续阶段，作**第二因素**而非唯一登录 |
| 微信扫码 | 强（持有微信） | 弱（二维码转发） | 怕微信被盗 / 封号 | 需白名单 + 二次确认 + `signAdmin` | 后续阶段，作**可选便捷入口** |
| **TOTP** | 强 | 弱 | 强（不依赖 SIM / 第三方） | **零依赖、自实现 RFC6238** | **本轮做** |
| Passkey / WebAuthn | 强 | **强（唯一抗钓鱼）** | 强 | 需域名绑定、凭据管理、浏览器兼容 | 远期 |

**短信 / 扫码的共同前提**（写进后续阶段的验收单，一条都不能省）：

1. 身份**预绑定**：服务端按 `username` 查 `admins.phone` 发码，**请求体绝不能有 phone**；扫码必须建 `openid ↔ 管理员` 白名单，绑定流程要求先密码登录。
2. 码 / 二维码短时、一次性、限次、绑定会话；发码接口自身严格限流（同号 60s / 每日 / 同 IP / 全局配额），码存 HMAC 不存明文。
3. 扫码必须加微信内「确认登录管理后台」二次点击并显示发起 IP / 地点，之后才 `confirmed`，且签发 `signAdmin`。
4. **必须有备用通道和一次性恢复码**：换号、微信封号、服务商宕机把自己锁在门外，比被攻击更常发生。

## 5. 分层设计

```
L0  服务端闸门     username + IP 双维限流 · 指数退避 · 恒定响应 · 统一报错 · 全量审计
L1  一次性挑战     图形验证码（字符转 path）+ PoW，按风险条件触发，答案只存 HMAC
L2  第二因素       TOTP（AES 加密入库）+ 一次性恢复码；密码正确后二段式换令牌
L3  会话与审计     token_epoch 可撤销 JWT · 登录成败写 admin_logs · 异动留痕
```

### 5.1 L0 具体改动

- `recentFailures` 从「只数 username」扩到 **username + IP 双维**，取较严者；
- 退避分级：5 次失败锁 15 分钟，再犯按 30 / 60 / 120 分钟指数递增（上限 24h）；
- 全局 IP 频控：同一 IP 跨账号登录 30 次 / 15 分钟即拦；
- **恒定时间**：用户名不存在时也用一个固定的 dummy hash 跑一次 `verifyPassword`，消除时序差；
- 成败都写 `admin_logs`（`admin_id=0` 表示未认证），记录 username / IP / UA / 结果；
- 报错保持统一文案，不区分「账号不存在 / 密码错 / 账号停用」以外的细节。

### 5.2 L1 具体改动

`GET /api/admin/challenge?scene=login` →

```json
{
  "challengeId": "ach_xxx",
  "svg": "<svg …>…</svg>",
  "expiresIn": 120,
  "pow": { "seed": "…", "difficulty": 16 }
}
```

- 验证码**自研零依赖**：4 位数字用 7 段数码管 `<path>` 绘制（**不能用 `<text>`**，否则 AI 读 DOM 直接拿答案），叠加随机倾斜、干扰线、噪点；答案不落明文，只存 `HMAC(主密钥, 答案)`；
- `admin_challenges` 表：`challenge_id / answer_hmac / pow_seed / ip / ua / expires_at / used_at / created_at`；
- 校验顺序：challenge 存在且未用且未过期且同 IP → PoW → 密码；**无论成败立刻置 used**；
- PoW：前后端共用 `public/assets/pow.js`（UMD，纯 JS 32 位混合哈希），前端循环找前 16 位为 0 的 nonce（几十毫秒、让出一帧避免卡首屏），服务端 O(1) 校验。**边界说清楚**：这是轻量摩擦层，专业攻击者可用原生代码加速到毫秒级，真正挡批量的是 L0 限流；不把它当密码学证明；
- 取 challenge 的接口自身限流（同 IP 20 次/分钟），否则成为新的放大入口；
- **条件触发**，设置项 `admin_captcha_mode` = `off | risk | always`，默认 `risk`：
  - `risk`：近 15 分钟该 IP 或该 username 有失败记录、或命中全局 IP 频控时才要求挑战；
  - `always`：每次登录都要求（测试用）；
  - `off`：关闭（应急）。
  - 这样正常管理员不弹码，且**现有自动化测试（全新库、无失败记录）不受影响**。

`POST /api/admin/login` 新增可选字段 `challengeId / answer / powNonce`。

### 5.3 L2 具体改动

零依赖实现 RFC 6238 TOTP（HMAC-SHA1、30s 步长、6 位、±1 步容差），`qrcode` 包生成 `otpauth://` 二维码。

- `admins` 加 `totp_secret`（`enc:` 前缀 AES-256-GCM）、`totp_enabled`、`totp_confirmed_at`、`token_epoch`；
- 已绑定 TOTP 的账号，密码校验通过后**不直接发 JWT**，返回：

```json
{ "needSecondFactor": true, "challengeToken": "…", "expiresIn": 300 }
```

  `challengeToken` 是一次性、5 分钟、绑定 admin_id + IP 的随机票据（存 `admin_challenges`，`purpose='2fa'`），不是 JWT、不带 scope。

- `POST /api/admin/login/2fa` 用 `challengeToken + code`（或恢复码）换正式 `signAdmin` 令牌；
- 绑定流程（需已登录）：`POST /api/admin/2fa/setup` → `{ otpauthUri, qrcodeSvg, recoveryPreview }`；`POST /api/admin/2fa/confirm` 用首个动态码确认启用，并返回 **10 个一次性恢复码（只显示一次）**，库里只存 hash；
- 设置项 `admin_2fa_nudge`：默认 `0`；打开后未绑定账号登录成功时响应带 `two_fa_suggested:true`，前端弹提示引导去绑定。**这是软引导、不是硬拦**——强制绑定需要配合受限令牌（类似 `mcp`），列入后续阶段；
- 恢复码用完即废；重新 setup 会使旧 secret 与旧恢复码全部失效。

### 5.4 L3 具体改动

- `signAdmin` 的 payload 加 `ep = admins.token_epoch`；`verifyAdmin` 校验时查库比对 `ep`，不一致即 401；
- 后台「强制下线」、解绑 TOTP 时 `token_epoch + 1`；**生产环境改密也会 +1**（`NODE_ENV=production`），测试 / 本地保持兼容（现有回归脚本会复用改密前签发的 `adminToken`），改密接口始终返回新令牌；
- 登录成功 / 失败、2FA 成功 / 失败、绑定 / 解绑、恢复码使用全写 `admin_logs`；
- 登录 IP 与上次不同写一条 `warn` 级日志（只留痕，先不阻断，避免误伤出差场景）。

| 变更 | 说明 |

## 7. 兼容性（必须守住）

- **现有 40+ 测试脚本**都用 `POST /api/admin/login {username,password}` 直接取 token。默认 `risk` 模式 + 默认 `admin_2fa_required=0` + 默认账号未绑定 TOTP → 全绿不受影响；
- `/auth/refresh` 等老开放接口**一律不套**新守卫；
- 所有新增路径都要带 `basePath()`（子路径部署）；
- 前端模板遵守：in-DOM 模板不写自闭合组件、Vue 模板不引用全局变量、弹层 `teleport to="body"`、IIFE 包裹；
- 401 只在 `api.js` 集中处理，登录接口自身 401 不清令牌。

## 8. 上线检查清单

1. `cd /opt/blcloud && git pull && pm2 restart blcloud-admin`；
2. 零凭据访问 `/platform/api/admin/challenge` 返回挑战（或按 `risk` 模式返回 `required:false`）；
3. 故意输错密码 1 次 → 再次登录应出现验证码；刷新验证码 / 过期 / 重放均被拒；
4. 后台「管理员」页绑定 TOTP，用验证器扫码；退出后重新登录走二段式；恢复码可用且用过即废；
5. 改密码后旧 JWT 立即 401（`token_epoch` 生效）；
6. 确认 `admin_logs` 能看到登录成败、IP、2FA 结果；
7. 生产确认 `devMode()` 恒 false、`/api/portal/phone/code` 不回 `devCode`、`/api/wechat/simulate/:scene` 与 `/api/pay/simulate/:orderNo` 后门关闭；
8. 备份包含 `data/.appsecret`（TOTP secret 依赖同一主密钥）。

### 实现口径与原设计的两处差异（有意为之）

1. **改密是否撤销旧令牌**按 `NODE_ENV` 分流：生产撤销、测试 / 本地不撤销。项目已有同类先例（弱口令受限令牌只在生产硬拦），这样既不牺牲生产安全，又不打断 40+ 回归脚本复用 `adminToken` 的现状。
2. **强制所有管理员启用 2FA** 从「硬拦」降级为「软引导」（`admin_2fa_nudge`）。硬拦需要一套受限令牌机制，风险是把还没绑定的人锁在后台门外；先让管理员自行绑定，等全部绑完再上硬拦。

## 9. 后续阶段（等外部条件，本轮不实现）

| 阶段 | 前置条件 | 内容 |
|---|---|---|
| S2 短信第二因素 | 短信账户审核通过 | 接真实发送通道；`admins.phone` 加密存；服务端查号发码；发码频控；码存 HMAC；与 TOTP 二选一作为第二因素 |
| S3 微信扫码便捷登录 | 服务号配置确认 | `admins.wechat_openid` 白名单；绑定流程；scene ≤2 分钟 + 一次性 + 微信内二次确认；签发 `signAdmin`；模拟后门与管理员会话彻底隔离 |
| S4 Passkey | 域名 / HTTPS 稳定 | WebAuthn 凭据绑定域名，唯一能抗实时钓鱼的方案 |
| S5 强制 2FA 硬拦 | 全部管理员绑定完成 | 参照 `mcp` 做受限令牌：未绑定账号只能访问 `/api/admin/2fa/*` 与 `/api/admin/me` |

**安全边界重申**：以上所有方案都挡不住针对管理员本人的实时钓鱼；内部后台靠管理员人数少 + 培训 + 审计告警控制该风险。
