# 客户端更新包接入（LabelGo 等桌面端）

> 面向 Electron / PC 客户端：**检查更新 → 拿到增量或全量包地址 → 下载 → 本地校验 sha256 → 安装**。
> 与 ThingsBoard 的 OTA / 固件包无关：包是普通文件，放磁盘、由 Nginx 直出，清单实时查库。

- 清单接口：`GET /api/open/v1/app/version?product=...`（公开，不鉴权）
- 下载地址：`{站点}/updates/<版本>/<包名>`（静态，支持 Range）
- 管理入口：后台 → 产品运营 → **客户端更新**
- 命令行发布：`node tools/publish-release.js ...`（大包/自动化用）

---

## 1. 接口契约

### 1.1 检查更新

```
GET /api/open/v1/app/version
  ?product=LabelGo          # 必填，缺省则走老的「应用信息」模式（要签名）
  &version=1.0.20           # 客户端当前版本
  &platform=win32           # 缺省 win32
  &arch=x64                 # 缺省 x64
  &channel=stable           # 缺省 stable
  &machine=BLBT-XXXX-XXXX   # 可选，灰度分桶用；建议一定带上
```

响应 `200 application/json; charset=utf-8`，头带 `Cache-Control: no-cache`：

```json
{
  "latest": "1.0.21",
  "channel": "stable",
  "report_url": "https://www.bliot.cn/platform/api/open/v1/app/update-report",
  "mandatory": false,
  "minVersion": "1.0.0",
  "changelog": "- 修复共享打印机被误判离线\n- 新增 600dpi 支持",
  "publishedAt": "2026-11-05T10:00:00Z",
  "full": {
    "url": "https://www.bliot.cn/platform/updates/1.0.21/LabelGo-1.0.21-full.zip",
    "sha256": "3f9c...（64 位小写十六进制）",
    "size": 1482000
  },
  "delta": [
    {
      "from": "1.0.20",
      "url": "https://www.bliot.cn/platform/updates/1.0.21/LabelGo-1.0.21-from-1.0.20.pkg",
      "sha256": "a71b...",
      "size": 168400
    }
  ],
  "product": "LabelGo",
  "current": "1.0.20",
  "update_available": true,
  "rollout": 100,
  "server_time": "2026-11-05T10:00:03.000Z"
}
```

已是最新时只回这些字段（**没有 `full` / `delta` 键**）：

```json
{ "product": "LabelGo", "channel": "stable", "latest": "1.0.20", "current": "1.0.20",
  "update_available": false, "no_release": false, "server_time": "...",
  "kid": "manifest-2026-11", "signature": "…" }
```

**这个产品一个包都没发布过**时（如离线版还没发首包），`latest` 是空串、并带 `no_release: true`：

```json
{ "product": "LabelGo-Offline", "latest": "", "current": "1.0.50",
  "update_available": false, "no_release": true, "auto_update": false, "server_time": "...",
  "kid": "manifest-2026-11", "signature": "…" }
```

这两种必须分开处理：`no_release:true` 表示「该产品暂无可用版本」，不要当成「已是最新」静默跳过，
更不要把 `current` 当成本次最新版（2026-11-11 复测时这里曾被误读成「拿到在线版清单」）。

客户端只需判断 `latest !== 当前版本`（或 `update_available`），不要假设 `full` 一定存在。

### 1.1.1 清单签名（2026-11-11 新增，客户端先软兼容）

响应体新增两个字段，**不改任何既有字段名**：

| 字段 | 说明 |
|---|---|
| `signature` | 对清单 body（去掉 `signature` 后的全部字段）做 Ed25519 签名，**base64**（64 字节） |
| `kid` | 密钥标识，形如 `manifest-2026-11`；**kid 本身在签名内容里**，换 kid 也验不过 |
| `auto_update` | `false` = 该产品不进自动升级（离线版只挂 `full`，由客户手动安装）。老客户端忽略即可 |

签名覆盖的是**每次响应的实时内容**（含 `server_time` / `rollout` / `mandatory`），
不是发布时签一次的静态文件 —— 否则灰度命中与否会被签成发布那一刻的样子。
静态兜底 `<产品>/latest.json`、`products.json`、根 `latest.json` 同样带签名（"一并加签"），
**签名直接写在 JSON 体内**，不生成独立 `.sig` 文件（少一个文件就少一处漏签）。

> 静态清单是「发布那一刻」写出来的，加签代码上线后不会自动重生成。
> 服务端启动时会自检：发现某份 `latest.json` / `products.json` 缺 `signature` 且已配置站点地址，
> 就按库里现有记录重建一次（日志会打印「更新清单已重建」）。
> 也可手动重建：后台「版本发布 → 重建兜底清单」，或服务器上
> `node tools/rebuild-manifests.js https://www.bliot.cn/platform`
> （自检不通过时脚本以非 0 退出，可挂进部署流程）。

**canonical 规则**（与服务端 `server/lib/signkey.js` 完全一致）：

1. 去掉 `signature` 键，其余键（含 `kid`）全保留；
2. 对象键按 Unicode 码点**字典序升序**；数组**保序**不排序；
3. 紧凑序列化：`{"a":1,"b":[1,2]}`，无空格、无换行；
4. `undefined` 字段不参与；`null` 参与；字符串按 JSON 标准转义；
5. 输出 UTF-8 字节串，对它做 Ed25519 验签。

**黄金向量（跨端自测用）**——固定样本（不含 `signature`）：

```json
{"kid":"manifest-2026-11","product":"LabelGo","channel":"stable","platform":"win32","arch":"x64",
 "latest":"1.0.50","mandatory":false,"minVersion":"1.0.0","current":"1.0.49",
 "update_available":true,"auto_update":true,"server_time":"2026-11-11T00:00:00.000Z",
 "report_url":"https://www.bliot.cn/platform/api/open/v1/app/update-report",
 "full":{"url":"https://www.bliot.cn/platform/updates/LabelGo/1.0.50/LabelGo-1.0.50-full.zip",
         "sha256":"aaaa…（64 个 a）","size":34567890},
 "delta":[{"from":"1.0.49",
           "url":"https://www.bliot.cn/platform/updates/LabelGo/1.0.50/LabelGo-1.0.49-to-1.0.50.diff.zip",
           "sha256":"bbbb…（64 个 b）","size":1400000}],
 "rollout":100,"changelog":"修复若干问题"}
```

- canonical 长度：**779 字节**
- SHA-256：`a6c9f696b03e2dc048bb4a0cf1f29d92babfcdcff56f205981a2184d256ebe26`

两端各自算这串，长度与哈希必须一模一样；不一样就是规则没对齐（常见差异：排了数组、
把 `kid` 排除在签名外、用了带空格的 `JSON.stringify(x, null, 2)`）。
本仓库自测：`node tools/test-manifest-sign.js`。

**公钥交付**：三把密钥相互独立，公钥构建期内嵌，运行时不得从网络拉：

| 用途 | kid 形如 | 取公钥（仅排障对照） |
|---|---|---|
| 更新清单 | `manifest-2026-11` | `GET /api/open/v1/app/keys` → `manifest` |
| 权益快照 | `ent-2026-11` | 同上 → `entitlement` |
| 离线票据 | 16 位哈希 | 同上 → `offline`（或老接口 `/app/pubkey`） |

`/app/keys` **需要带 `X-App-Key`**（公开模式即可，不用签名；带有效 Bearer 也放行）：
公钥本身不是机密，要求带 key 只是防批量爬取。裸请求回 `401 APP_KEY_REQUIRED`，
不是密钥配错，构建期取公钥时记得带上应用标识。

过渡策略：**有签名就验，验不过拒绝安装并上报 `code=1/stage=download`**；
老版本客户端不认识 `signature`，自然忽略（向后兼容）。
等服务端确认全量客户端已升级（后台「开放应用 → 鉴权模式 / 升级记录」）后再转强制。


### 1.2 客户端判定规则

| 情况 | 行为 |
|---|---|
| `no_release === true` | 该产品暂无任何发布记录：提示「暂无可用版本」，**不当作已最新**，仍可正常使用当前版本 |
| `latest` 等于当前版本 | 已是最新，继续运行 |
| `latest` 比当前新 + 有 `delta` 中 `from === 当前版本` | 走增量包（省流量） |
| `latest` 比当前新 + 无匹配 `delta` | 走 `full` |
| `mandatory === true` 或 `version < minVersion` | 弹**阻断窗**，不升级不给用 |

`sha256` / `size` 必须校验：下载完先算，不符直接丢弃并重试一次 full。
服务端给的这两个值来自**落盘时实际计算的哈希**，不是让管理员手填的，所以只要文件没被改动就一定对得上。

### 1.3 其它约定

- 所有 `url` 都是**绝对地址**（含 `https://` 与 `/platform` 子路径），Electron 主进程直接 `net.request` / `download` 即可，不要拿页面相对路径拼。
- 下载**不鉴权、不重定向到登录页**：客户端没登录也要能升级；包本身有哈希，且不是机密。
- 清单**不缓存**（`no-cache`），发包后下一次轮询就能拿到。
- 同一路径 `GET /app/version` **不带 `product`** 时仍是老的「应用信息」接口（要 `X-App-Key` 签名），老客户端不受影响。
- 清单响应里带 `report_url`，客户端升级完调一次它，后台就能看到「谁真的升了」。

### 1.4 升级结果上报（契约 v2，2026-11-10 与 LabelGo 客户端逐字段对齐）

```
POST {report_url}                      # 即 /api/open/v1/app/update-report
Content-Type: application/json         # 不需要任何签名头 / 令牌

{
  "product": "LabelGo",                // 必填，其余全部可选
  "machine_code": "硬盘序列号哈希",      // 兼容旧字段 machine
  "from_version": "1.0.49",            // 兼容 from
  "to_version": "1.0.50",              // 兼容 to / target
  "result": "success | fail | rollback",   // 兼容旧 status；failed/error → fail
  "code": 0,                           // 失败码（整数）：0 成功；1 下载/校验失败（stage=download）；
                                       // 2 解包失败（stage=extract）；3 已提权仍不可写；
                                       // 4 旧进程结束不掉；5 覆盖失败；6 新版本未起来；
                                       // 7 UAC 被取消；8 launch_failed（三兜底全挂）
  "stage": "download | extract | precheck | elevate | close | copy | launch | alive",
  "duration_ms": 23400,
  "elevated": true,
  "os": "10.0.19045",
  "at": "2026-11-10T14:14:24Z",        // 客户端时间（离线补报时后台按它展示）
  "note": ""                           // 附加说明（后台备注列直接显示）
}
```

返回 `{"ok":true,"id":123,"action":"success","deduped":false}`。
`deduped:true` 表示覆盖了一条旧结果（重试/回滚后重升的场景）。

**去重口径：覆盖，不累加。** 同一台机器（machine_code）+ 同一组 from→version 的结果
只保留最新一条：上报失败本地重试 7 天、回滚后重升成功，都不会把后台的失败次数灌水；
清单命中（check）流水不受影响。machine_code 缺省（老客户端）时退化为普通流水不去重。

**不接也能用**：客户端只要来查清单，后台就会记录一条「命中」（同一机器 10 分钟内同一
目标版本只存一条）。只有接了上报，才能区分「真升成功」「失败在哪一步」「谁回滚了」。
后台「客户端更新 → 升级记录」可查（失败/回滚行直接显示 code · stage · 耗时 · OS · 是否提权）。

**失败码口径（2026-11-11 定稿，含客户端提的 1/2）**：

| code | 含义 | 典型 stage |
|---|---|---|
| 0 | 成功 | — |
| 1 | 下载/校验失败（网络、sha256/size 不符、清单验签失败） | `download` |
| 2 | 解包失败（zip 损坏、路径非法、磁盘不足） | `extract` |
| 3 | 已提权仍不可写 | `copy` |
| 4 | 旧进程结束不掉 | `close` |
| 5 | 覆盖失败 | `copy` |
| 6 | 新版本未起来 | `launch` |
| 7 | UAC 被取消 | `elevate` |
| 8 | launch_failed（三兜底全挂） | `alive` |

后台「升级记录」直接把 code 显示成中文标签；未知 code 原样显示，不吞。

### 1.4.1 与软件方契约逐条对照（2026-11-10 复核）

| 契约 | 状态 | 说明 |
|---|---|---|
| 清单字段 `latest / channel / mandatory / minVersion / changelog / publishedAt / full / delta` | 已实现 | `publishedAt` 统一为 ISO 8601 秒级 UTC（`…Z`）；额外多给 `product / current / update_available / rollout / report_url / server_time`，客户端忽略即可 |
| 无新版本 → `200 {"latest":"<当前版本>"}` 或 204 | 已实现 | 选 200，且不带 `full` / `delta` |
| `delta[]` 按 `from` 挑、无匹配用 full | 已实现 | `delta` 按 from 倒序，没有匹配时 `[]` |
| `mandatory=true` 或 `version < minVersion` → 阻断 | 已实现 | 服务端已把「低于 minVersion」合并进 `mandatory`，客户端只看一个字段即可 |
| URL 为可直 GET 的 HTTPS 绝对地址、不鉴权不跳转 | 已实现 | 见下方 HTTPS 依赖 |
| sha256 小写十六进制、size 字节数 | 已实现 | 发布时流式落盘同时算，测试逐字节比对 |
| `Cache-Control: no-cache` | 已实现 | 清单接口与 `latest.json` 都是 no-cache，包文件是 immutable |
| 静态目录 / Range / 目录不可列 / octet-stream / 禁脚本 | 已实现 | Nginx 段在 `deploy/nginx-subpath.conf`；不配也能用（后端 `@fastify/static` 兜底，同样支持 Range） |
| `client_max_body_size 50m` | **有意放宽到 200m** | 单次上传限制在应用层（64MB），Nginx 放宽只是不先一步挡住，功能上是契约的超集 |
| 灰度 10% → 全量 / 回滚 | 已实现 | `rollout` 0–100 按 `machine\|version` 哈希分桶；回滚 = 停用新版本或改回启用旧版本 |
| 不用 ThingsBoard OTA / 设备属性 | 已遵守 | 全链路只用本地磁盘 + `app_release` 表 |

**HTTPS 是部署依赖，不是代码默认值**：清单里的绝对地址按当前请求现拼（`publicUrl()`），生产要同时满足
① Nginx 有 `proxy_set_header X-Forwarded-Proto $scheme;`（配置已带）
② PM2 环境 `TRUST_PROXY=1`（`ecosystem.config.cjs` 已带）
缺一个，接口就可能回 `http://…`，Electron 主进程下载会被拦。
而兜底 `latest.json` 里的地址是**发布那一刻**从 `PUBLIC_BASE_URL` / 后台「对外地址」写死的，
换域名或换子路径后必须点一次后台「重建清单」（或重跑发布 CLI），否则仍然指向旧域名。

## 2. 静态目录

```
data/updates/                                  ← 物理目录（UPDATES_DIR 可改）
  latest.json                                  ← 默认产品的兜底清单（老客户端/文档兼容）
  products.json                                ← 产品索引：有哪些产品、各自最新版、清单地址
  LabelGo/
    latest.json                                ← LabelGo 自己的兜底清单
  TestPad/
    latest.json                                ← 每个产品各一份
  1.0.21/
    LabelGo-1.0.21-full.zip
    LabelGo-1.0.21-from-1.0.20.pkg
```

**多产品**：`product` 是清单接口的第一查询参数，`app_release` 按 产品+渠道+平台+架构+版本 唯一，
不同产品各自独立发版、互不影响。新增产品不需要任何登记——发布时填个新产品名即可。
兜底清单每产品一份（`<产品>/latest.json`），根目录 `latest.json` 固定给「默认产品」（后台可配）。

对外的 URL 是 `{站点}/updates/...`（子路径部署即 `https://www.bliot.cn/platform/updates/...`）。

> 目录权限：`chown -R <运行用户> data/updates`，Nginx 需要读权限（`chmod 755` 目录、`644` 文件）。
> **账套备份不打包这个目录**（包是构建产物，几十 MB 起），换服务器时需单独同步 `data/updates`。

`products.json` 结构（带签名，与 `<产品>/latest.json` 同规则）：

```json
{
  "generated_at": "2026-11-11T13:40:00.000Z",
  "manual_products": ["LabelGo-Offline"],
  "products": [
    { "product": "LabelGo", "latest": "1.0.51", "channel": "stable", "platform": "win32",
      "auto_update": true, "manifest_url": "https://…/updates/LabelGo/latest.json" },
    { "product": "LabelGo-Offline", "latest": "1.0.51", "channel": "stable", "platform": "win32",
      "auto_update": false, "manifest_url": "https://…/updates/LabelGo-Offline/latest.json" }
  ],
  "kid": "manifest-2026-11", "signature": "…"
}
```

- **只有发过一次包的产品才会进 `products` 数组**：没发过就没有 `latest` 可写，
  塞一条空记录只会让客户端拿到 404 清单。`manual_products` 用来提前告知「这个产品存在但需手动安装」。
- `auto_update: false` 的产品（默认 `LabelGo-Offline`，后台 `release_manual_products` 可改）
  只挂全量包、不进自动升级；两个产品的增量基线互不混用。

- 目录**不可列**：Node 侧 `index/list` 全关；Nginx 侧 `autoindex off`。访问 `.../1.0.21/` 得到 404。
- 包响应头：`Cache-Control: public, max-age=31536000, immutable` + `Content-Type: application/octet-stream` + `Accept-Ranges: bytes`（断点续传）。
- `latest.json` 响应头：`Cache-Control: no-cache`。
- 目录只读：Nginx `limit_except GET HEAD { deny all; }`。

### 2.1 Nginx（可选，但建议）

不配也能用（后端自带静态托管，Range 同样支持）；配了之后大文件不经过 Node。
完整段落见 `deploy/nginx-subpath.conf` 方案 B，关键点：

```nginx
location ^~ /platform/updates/ {
    alias /opt/blcloud/data/updates/;        # 与 UPDATES_DIR 一致
    autoindex off;
    types { application/json json; }
    default_type application/octet-stream;
    limit_except GET HEAD { deny all; }
    add_header Accept-Ranges bytes always;
    set $release_cc "public, max-age=31536000, immutable";
    if ($uri ~* "\.json$") { set $release_cc "no-cache"; }
    add_header Cache-Control $release_cc always;
    if ($uri ~* "\.(php|jsp|asp|aspx|cgi|sh|pl|html?|svg|js)$") { return 403; }
}
```

> 必须放在 `location ^~ /platform/` **前面**（`^~` 最长前缀匹配，nginx 会自己选，但别写成正则）。
> `client_max_body_size` 是**上传口**的限制，配在反代的 `/platform/` 上（当前 200m，同时覆盖账套备份包）；
> 客户端下载不受它影响。Node 侧单次上传上限 64MB。

## 3. 发布

### 3.1 后台发布（日常用）

后台 → 产品运营 → **客户端更新**：

1. 填产品（默认 LabelGo）、版本号（如 `1.0.21`）、渠道/平台/架构；
2. 选全量包 zip（≤64MB）；
3. 可选：选增量包 + 来源版本（如 `1.0.20`）；
4. 填最低版本、灰度比例、更新说明，勾选是否强制；
5. 「上传并发布」——文件落到 `版本目录/`，记录进库，`latest.json` 同时重建。

页面底部「客户端会看到什么」可以模拟任意版本 + 机器码，直接看返回的 JSON，不用真装机。

### 3.2 命令行发布（大包 / CI）

```bash
# 全量 + 增量一起发
node tools/publish-release.js \
  --version 1.0.21 \
  --file  dist/LabelGo-1.0.21-full.zip \
  --delta dist/LabelGo-1.0.21-from-1.0.20.pkg --from 1.0.20 \
  --min-version 1.0.0 \
  --changelog-file dist/CHANGELOG.txt \
  --site https://www.bliot.cn/platform
```

常用参数：`--product --channel --platform --arch --mandatory --rollout 10 --disabled --full-url`
（包放 CDN 时用 `--full-url` 覆盖地址）。

命令只写本地文件 + 数据库，不联网；服务器上直接 scp 完再跑也成立。

### 3.3 灰度

`rollout` 0–100：按 `sha256(machine + "|" + 版本)` 取模分桶，同一台机器每次都落在同一桶。

- `100` 全量；`10` 先给约 10% 的机器；
- `0` 暂停下发（比删除安全，随时拉回 100）；
- 客户端没带 `machine` 时按「命中」处理，所以**想整体暂停请用 0 或停用**；
- 高版本只覆盖了 10%，剩下 90% 会继续拿到上一个**全量**版本，不会被卡住。

兜底清单（每产品的 `<产品>/latest.json` 与根 `latest.json`）只写**全量（rollout=100）**的最高版本——静态文件没法按机器分桶，写灰度版会坑到所有人。

> 目前按 `machine` 分桶；按「客户/租户分组」灰度还没做（需要先有稳定的分组标识）。
> 现阶段想按客户放量，可以让客户端把客户编号拼进 `machine`，或者直接分批改 `rollout`。

### 3.4 回滚

客户端只认「比当前新」的版本，把 `latest` 指回旧版**不会**触发降级。真要收回：

1. 后台把出问题的版本「停用」——新客户端不再收到它；
2. 若必须让已升级的机器退回去：发一个**版本号更高**的修复版（如 1.0.22），配 `mandatory` + 说明。

## 4. 数据表 `app_release`

| 列 | 说明 |
|---|---|
| `product / channel / platform / arch / version` | 唯一键，同组合重复发布即替换 |
| `full_path` | 相对 `updates/` 的路径（存相对路径，换域名不会变死链） |
| `full_url` | 可选，走 CDN 时填绝对地址；留空按请求现拼 |
| `full_sha256 / full_size` | 落盘时实际计算 |
| `delta_json` | `[{from, path, sha256, size}]` |
| `mandatory / min_version / changelog` | 客户端提示与阻断依据 |
| `rollout / published_at / enabled` | 灰度、发布时间、上下线 |

## 4.1 数据表 `app_update_log`（升级流水）

| 列 | 说明 |
|---|---|
| `product / channel / platform / arch` | 哪条产品线 |
| `machine` | 客户端机器码（灰度分桶用的同一个） |
| `from_version / to_version` | 版本变化 |
| `action` | `check`=清单命中、`success`=升级成功、`fail`=升级失败 |
| `ip / user_agent / note` | 排障用；failed 的 note 一般是错误摘要 |
| `created_at` | 事件时间 |

这张表只增不改，量大了按 `created_at` 定期清理即可（不影响授权与发布记录）。

## 5. 验收

```bash
B=https://www.bliot.cn/platform

# 1. 有更新
curl -s "$B/api/open/v1/app/version?product=LabelGo&version=1.0.20&platform=win32&arch=x64" | jq .

# 2. 已是最新
curl -s "$B/api/open/v1/app/version?product=LabelGo&version=1.0.21" | jq .latest

# 3. 包可下、长度对、支持断点
curl -sI "$B/updates/1.0.21/LabelGo-1.0.21-full.zip"        # 200 + Accept-Ranges + Content-Length
curl -s -r 0-1023 "$B/updates/1.0.21/LabelGo-1.0.21-full.zip" -o /tmp/part
stat -c%s /tmp/part                                          # 1024

# 4. 校验值与清单一致
curl -s "$B/updates/1.0.21/LabelGo-1.0.21-full.zip" | sha256sum

# 5. 目录不可列
curl -s -o /dev/null -w "%{http_code}\n" "$B/updates/1.0.21/"     # 403/404

# 6. 兜底清单
curl -s "$B/updates/latest.json" | jq .
```

后台「客户端更新 → 校验」会对磁盘文件重算 sha256 并与库里的比对，文件被改过会直接标红。

## 6. 排障

| 现象 | 先看哪里 |
|---|---|
| 清单 404 | 请求的是 `/platform/api/open/v1/app/version` 吗？少了 `product` 会走签名模式（401） |
| 清单里 `latest` 一直是旧版 | 是不是 `channel/platform/arch` 与发布时不一致；是不是该版本被停用或 `rollout=0` |
| 下载 404 | 后台列表里「文件缺失」标记；Nginx alias 是否指向 `data/updates/` |
| 下载 302 到登录页 | Nginx 把 `/updates/` 也代理给了后端鉴权路由；按第 2.1 节加独立 location |
| 客户端校验失败 | 点「校验」重算哈希；确认下载时没被 CDN 改写（如 gzip 压缩二进制） |
| Range 不生效 | `Accept-Ranges` 是否丢失；Nginx 是否开了 gzip 压缩包文件（应关闭） |
| 清单里的 url 是 `http://` | 反代没传 `X-Forwarded-Proto`，或后端没开 `TRUST_PROXY=1`。生产必须下发 https 地址，否则 Electron 可能被混合内容策略拦 |
| 发了版客户端收不到 | 客户端缓存？清单是 `no-cache`；确认它请求的是新地址而不是 `latest.json` 的旧副本 |

## 7. 明确不做

- 不把包 base64 塞进 ThingsBoard 设备属性 / 遥测，也不用 TB 的 OTA 固件接口；
- 下载接口不鉴权、不重定向到 SSO；
- 清单里不返回相对路径（Electron 主进程不认页面相对路径）。
