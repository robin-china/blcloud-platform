## 一、三条书面回执

### 1) `LabelGo-Offline` 产品名：**采用**

- 升级系统里 `app_release.product` 是**自由文本**，不需要预登记；发布时产品名填 `LabelGo-Offline` 即可，
  会自动生成 `updates/LabelGo-Offline/latest.json`。
- 唯一性按 `(product, channel, platform, arch, version)`，两个产品的包天然隔离，增量基线不会串。
- 根 `updates/latest.json` **固定给默认产品**（`release_default_product`，当前 `LabelGo`），离线产品只在自己的目录下。
- 离线产品默认 `auto_update:false`（设置项 `release_manual_products` 默认 `LabelGo-Offline`）：
  清单照常下发、包照常可下，但客户端不应自动装 —— 由实施/客户手动安装。
- 两个维度已拆开：
  - **升级通道** = `app_release.product`（LabelGo / LabelGo-Offline），配在「开放应用 → 升级通道产品名」；
  - **权益维度** = `products.sku`（在线 3 款 / 离线 2 款共用同一套权益码），配在商品表单。
  两者没有混成一列。

### 2) 静态兜底 `latest.json` / `products.json`：**一并加签**

已实现，不是「只读不装」：

- `updates/<产品>/latest.json`、`updates/products.json`、`updates/latest.json` 都带 `signature` + `kid`；
- 与动态清单同一把密钥、同一 canonical 规则；
- 静态文件里的 `auto_update` 同样按产品写入。

理由：只签动态响应，等于留了一个「改 hosts / 改 DNS 指向静态文件就能装任意包」的入口，
而 sha256 也在同一份清单里 —— 攻击者连哈希一起改就行。

### 3) 不带 `product` 的 `/app/version`（老「应用信息」接口）：**不受影响**

- 该分支保持原行为：返回 `id / app_key / name / version / offline_days / plan_catalog` 等，
  **没有加 signature，也没有改成必须令牌**；
- 双模期它同时接受 HMAC（新/旧密钥）、公开模式、Bearer 令牌；老客户端只带四件套照旧 200；
- 更新清单分支（带 `product`）依旧**不鉴权**，只多返回 `signature` / `kid` / `auto_update`，老客户端忽略即可。

### 关于「加购包完整并集」的说明（需要你们确认口径）

后台当前**没有「加购包」这个实体**：权益就是档位配置的 `features[]`，
每次 verify / heartbeat / 换票都**全量下发该档位的完整清单**（不是增量），
客户端按 `features.includes(token)` 判定即可。

如果你们的「加购包」是指「在某个已售授权上单独追加若干能力码」（不换档位、不改价），
那需要新增一层存储（建议 `licenses.extra_features`，下发时 `档位 features ∪ 加购 features`）。
**这一层本期没做**，因为涉及下单/退款/续期的权益回收，得先定清楚业务规则再动。
请回一句：加购是「独立商品、买完并入这张码」还是「就是一个更高档位」——
前者我们再排期，后者现在就能用（新建档位即可）。

## 三、签名规则与黄金向量（跨端必须对齐）

**canonical**：去掉 `signature` 键 → 键按字典序 → 紧凑无空白 → 数组保序 → UTF-8 → Ed25519。
`kid` 在签名内容里（换 kid 也验不过）。

黄金向量（完整的固定样本见 `docs/客户端更新包接入.md §1.1.1`）：

- canonical 长度：**779 字节**
- SHA-256：`a6c9f696b03e2dc048bb4a0cf1f29d92babfcdcff56f205981a2184d256ebe26`

> 注意：你们草案里给的「480 B / `54d750f2…`」是另一份样本（字段更少的清单）算出来的，
> 与我们的固定样本不可比。两边各自跑自己的样本永远对不上，请以文档里这份样本为准对齐一次；
> 对齐通过后，再拿线上真实响应做一次端到端验签即可。

三把密钥互相独立、分别内嵌：

| 用途 | kid 前缀 | 取公钥 |
|---|---|---|
| 更新清单 | `manifest-` | `GET /api/open/v1/app/keys` → `manifest` |
| 权益快照 | `ent-` | 同上 → `entitlement` |
| 离线票据 | 16 位哈希 | 同上 → `offline` |

私钥只落在服务器 `data/*.json`（0600），与 `.appsecret` 一起备份；轮换只需换文件 + 重发公钥。

## 四、后台操作顺序（部署后照这个走）

1. **先部署**（`cd /opt/blcloud && git pull && pm2 restart blcloud-admin`）。
   首次启动会生成 `data/manifest-signing-key.json`、`data/entitlement-signing-key.json`，**立即纳入备份**。
2. **轮换应用密钥**：后台「开放应用 → 轮换密钥」→ 新值只存后台/构建机，旧值自动进并存通道。
   不要点「重置密钥」（硬重置立刻作废旧值 + 踢所有会话）。
3. **观察**：「鉴权模式（近 14 天）」里 `旧密钥签名` 连续 7 天为 0 → 点「关旧密钥」。
   此时旧客户端会收到 `401 APP_SECRET_RETIRED`（明确提示该升级，不是密钥写错）。
4. **公开模式**：新客户端只带 `x-app-key`（写请求带 `x-nonce`）即可；如要收紧，逐应用关「公开」。
5. **离线产品**：发布时产品名填 `LabelGo-Offline`，只挂 full；客户端按 `auto_update:false` 不自动装。
6. **停票**：授权详情 → 机器 → 停票（`POST /api/licenses/:id/ticket/stop`），
   `epoch +1` 让已发票立即失效，下一换票周期返回 `TICKET_STOPPED`。
7. **词表**：LabelGo 应用 → 「填入示例词表」→ 确认包含 `labelgo.erp_conn` → 保存。

# 复测回执（2026-11-11 21:40，对应客户端 4 项复测反馈）

## 1. 静态兜底重签 —— 已修（代码 + 启动自愈）

现象确认：三份静态清单停在 `2026-11-10T16:17:05.340Z`，无 `signature`/`kid`。
原因不是没写加签代码，而是**静态清单只在「发布版本」那一刻生成**，加签代码上线不会触发重生成。
另外**不会生成独立 `.sig` 文件**：签名直接写在 JSON 体内（`signature` + `kid`），
少一个文件就少一处漏签，客户端只读 JSON 即可。

本次落地三件事：

1. **启动自愈**：服务启动时检查每份 `updates/*/latest.json`、`products.json`、根 `latest.json`，
   缺签名且已配置站点地址（`PUBLIC_BASE_URL` 或后台「版本发布 → 站点地址」）就按库里记录重建一次，
   日志打印「更新清单已重建：…」。没配站点地址时只告警不重建（避免把绝对下载地址写成相对路径）。
2. **命令行重建**：`node tools/rebuild-manifests.js https://www.bliot.cn/platform`，
   写完后自检，仍缺签名则以非 0 退出，可挂到部署脚本里。
3. **后台手动**：「版本发布 → 重建兜底清单」（原有按钮，现在会带上签名）。

结论：**「一并加签」的书面答复不变**，且不再依赖人工记得点按钮。

## 2. 离线产品索引与包隔离 —— 已修（一处真 bug）

`products.json` 只有 `LabelGo` 是**预期**：索引只列「发过包的产品」，没发过就没有 `latest` 可写。
真正的问题是动态接口：`?product=LabelGo-Offline` 在没有任何发布记录时，
把请求里的 `version` 原样回显成 `latest`（你们传 1.0.51 就看到 1.0.51），
`update_available:false` —— 客户端会误判成「已是最新，且最新版就是在线版那个」。
离线包一旦没发，这个谎会一直存在。

改为：**没有任何发布记录时回 `latest:""` + `no_release:true`**，不带 `full`/`delta`；
有记录但已最新时才回 `latest=当前版本` + `no_release:false`。
同时 `products.json` 增加 `manual_products:["LabelGo-Offline"]` 与每项 `auto_update`，
让客户端能区分「没这个产品」和「有这个产品但还没发包」。

离线包隔离本身没有串：包名按产品生成（`LabelGo-Offline-1.0.51-full.zip`），
清单按 `app_release.product` 分目录（`updates/LabelGo-Offline/latest.json`），
增量基线按产品各自匹配。发布后 `products.json` 会自动多一条，无需登记。

## 3. `/app/keys` 需要 `X-App-Key` —— 确认是预期

公钥不是机密（本来就要内嵌进安装包），要求带 key 只是防批量爬取。
裸请求现在回 **`401 APP_KEY_REQUIRED`**（原来是笼统的 `UNAUTHORIZED`，容易误判成密钥配错）。
公开模式即可取，不需要签名；带有效 Bearer 也放行。你们「构建期内嵌、运行时不拉」的做法是对的。

## 4. HMAC 口径 —— 确认：path 含查询串

`path` 取原始请求行（`req.url`），含 `/api/open/v1` 前缀，**带查询串时整串入签**。
只算 pathname 必然 401，这不是 bug。字段、算法、拼接顺序都不改。

关停时间表（详见 `docs/软件端接入API.md` §2.2.2）。**基准改为首个正式发售版本发布日 T0**，
1.0.52 / 1.0.53 是内部测试包（仍内置明文 appSecret、未对外分发），不计入统计：

| 阶段 | 时点 | 动作 | 通过条件 |
|---|---|---|---|
| S0 | 现在 | 双模全放行 | — |
| S1 | **T0** | 发售包一次性落地 C 批（去 appSecret + 强制验签 + 双产物隔离） | 发售包通过验收且为唯一对外可分发的包 |
| S2 | **T0 + 7d** | 后台「关旧密钥」 | 发售日起 `hmac_legacy` 连续 7 天为 0 |
| S3 | **S2 + 30d** | 移除 `hmac_legacy` 分支 | 期间无回滚 |

「新版覆盖 ≥95%」作废：发售前外部用户为 0，没有分母。S1 的判据只能是发售包本身。
7 天观察期实际只兜内部测试机；外部客户第一天就在发售包上，本就不走旧通道。

建议 T0 之前做一次**密钥轮换**（不是「重置密钥」）：让测试包里的明文值降为 `app_secret_prev`，
S2 关掉即彻底失效；不轮换则测试期泄露的那个值会一直以「当前密钥」身份活着。

**S2 之前别删 appSecret**：`APP_SECRET_RETIRED` 是「旧密钥已停用」的信号，
让客户端能分辨「该升级」和「密钥写错了」，提前删就失去这个判断依据。
