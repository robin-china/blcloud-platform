## 二、微信服务号（扫码登录）

### 2.1 后台自检

后台 → **系统设置 → 接入配置 → 微信服务号** → 点「测试连接」。

成功提示「服务号配置可用」。这一步实际是拿 AppID + AppSecret 去换 access_token，能通就说明这两个字段没错。

### 2.2 微信后台要核对的四项

| 微信后台位置 | 应填的值 |
|---|---|
| 服务器地址 URL | `https://www.bliot.cn/platform/api/wechat/server` |
| 令牌 Token | 与后台「消息校验 Token」**完全一致** |
| 消息加解密密钥 | 与后台「消息加密密钥」一致（选安全模式时） |
| IP 白名单 | 服务器公网 IP：`211.149.164.*` |

改完在微信后台点「启用」。如果提示 URL 验证失败，看服务器日志：

```bash
pm2 logs blcloud-admin --lines 50
```

### 2.3 关键判断：二维码是不是真的

打开 `https://www.bliot.cn/platform/user/` 点微信登录，然后：

```bash
# 服务器上直接请求生成二维码的接口，看返回的 mode
curl -s -X POST https://www.bliot.cn/platform/api/wechat/qrcode
```

返回里的 `mode` 字段是关键：

| mode 值 | 含义 |
|---|---|
| `"wechat"` | ✅ 真实微信二维码，配置正常 |
| `"simulate"` | ⚠️ 后台压根没读到 AppID/AppSecret（多半是没勾「启用」或没保存） |
| `"error"` | ❌ 配置已填但调微信失败，看同一响应里的 `error` 字段（已翻译成中文处理建议） |

### 2.4 真机扫码

微信扫那个码 → 公众号会推「登录成功，请返回网页继续操作」→ 网页自动跳进用户中心。

### 2.5 扫码后网页不动：先点「回调诊断」而不是先 ssh

后台 → **系统设置 → 接入配置 → 微信服务号** → 点「回调诊断」。这一步把「微信到底有没有打过来」
和「打过来了但处理失败」彻底分开，不用登录服务器翻日志：

| 面板显示 | 说明 | 怎么做 |
|---|---|---|
| 一条推送记录都没有 | 微信的请求根本没到本机 | 检查微信后台「服务器配置」是否点了**启用**，URL 是不是面板给出的那个地址；再查 nginx：`grep "wechat/server" /var/log/nginx/access.log \| tail -5` |
| 有「收到微信推送」但没有「扫码登录成功」 | 到了但没处理成功 | 面板会直接写原因，常见是 `decrypt` 解密失败（EncodingAESKey 填错）或 `signature` 验签失败（Token 不一致） |
| 有 `[ok] login 扫码登录成功` | 服务端已完成登录 | 网页不跳多半是前端轮询问题，看浏览器控制台网络面板里 `/api/wechat/qrcode/<scene>` 的返回 |

历史坑（代码层面已修，这里留作判断依据）：微信 POST 的是 **XML**，早期版本没注册 XML 解析器，
请求在 body parser 阶段就被 **415** 拒掉，handler 一行都不执行 —— nginx 日志有记录、
业务日志完全空白，就是这个症状。现在看到 415 说明部署的代码不是最新版。

补充命令（需要看历史或排别的故障时）：

```bash
pm2 logs blcloud-admin --lines 50
grep "wechat/server" /var/log/nginx/access.log | tail -5
```

> 注意：诊断面板的事件存在进程内存里（最多 30 条），**`pm2 restart` 会清空**；
> 要看更早的故障仍然得用 `pm2 logs`。

## 三、微信支付

### 3.1 后台自检（新增能力）

后台 → **系统设置 → 接入配置 → 微信支付 v3** → 点「测试连接」。

这一步**不需要真实付款**，会用商户私钥向微信发一次查询请求（查一个不存在的订单），验证：

- 商户号 + 证书序列号 + 商户私钥 → 请求签名被微信接受
- API v3 密钥 → 长度必须是 32 位（平台证书模式下还会实际解密证书，可完整验证内容）

两种验签模式，测试通过后 message 会写明当前是哪一种：

| 后台「验签模式」 | 条件 | 回调怎么验签 |
|---|---|---|
| 微信支付公钥（本地验签） | 填了「微信支付公钥内容」 | 用本地公钥验签，**不联网**，新商户号必须走这条 |
| 手动平台证书 | 填了手动平台证书 | 用本地证书验签 |
| 自动下载平台证书 | 上面两项都没填 | 联网拉 `/v3/certificates`，老商户号可用 |

常见报错对照：

| 报错 | 原因 |
|---|---|
| 缺少配置：xxx | 字段没填全 |
| `Http status 401` / 签名错误 | 证书序列号串错了（必须不含 `serial=`，不含冒号）或私钥粘漏了首尾两行 |
| `Http status 403` / 商户号不匹配 | AppID 和商户号没绑定，去商户平台做关联授权 |
| `unsupported state or unable to authenticate data` | **API v3 密钥填错**（解密失败），回商户平台重置一个再填 |
| `RESOURCE_NOT_EXISTS` / 无可用的平台证书 | 该商户号**已不支持下载平台证书**：去 API安全 申请「微信支付公钥」，把公钥ID与公钥内容填到后台 |
| 微信支付回调验签失败 … Wechatpay-Serial=xxx | 公钥内容与商户平台下载的不一致，或公钥ID填错（回显的 serial 就是微信侧实际使用的） |

### 3.2 商户平台要核对

- 产品中心 → 已开通 **Native 支付**（系统走的就是扫码付）
- 产品中心 → 开发配置 → **支付回调域名** 填 `www.bliot.cn`
  （**不带路径**，路径 `/platform/api/pay/notify/wxpay` 由系统按 `BASE_PATH` 自动拼）
- API 安全 → 已申请 API 证书，拿到 `apiclient_key.pem`

### 3.3 真实支付全流程（0.01 元）

1. 准备一个有价格、已上架的产品（后台 → 产品管理）
2. 微信扫码登录用户端 → 进产品详情 → 下单 → 选微信支付
3. 页面弹出二维码 → 用微信扫
4. **付 1 分钱**

期望结果：

- 支付完成后页面自动跳到订单详情，状态变「已支付」
- 后台 → 交易管理 → 订单里这笔是 `已支付`，有 `trade_no`
- 后台 → 授权管理里自动生成了授权码（如果产品配了授权）
- 订单列表会显示**「已发放：…」**（授权码 / API 额度 N 次）。
  **「已支付」不等于「已发货」**：若这里显示「未发放任何内容」，说明商品被删或发货出错，要查支付诊断

> 「服务」类商品（API 额度包）发的是 **API 调用额度**（充进用户账户额度池，用户端 blcloud 页可见），
> **不发授权码**。额度数量取商品上显式填的「API 额度（次）」，没填才按名称/副标题里的「N 万次」猜，
> 猜不出按 10 万次 —— **上线前务必给额度包显式填这个数字**，否则用户买到的与页面标称不符。

> 每次测试都要**新建订单**。同一商户号下 `out_trade_no` 不能重复，拿旧订单再付会报「订单号重复」。

### 3.4 回调没到账怎么查

**这是最容易出问题的地方**，因为支付成功但回调没到，用户付了钱拿不到授权。

服务器上：

```bash
# ① 看 nginx 有没有收到回调
grep "notify/wxpay" /var/log/nginx/access.log | tail -5

# ② 看应用日志
pm2 logs blcloud-admin --lines 100 | grep -i pay

# ③ 直接查支付流水表（payments 记录所有回调尝试，status 能看出是 success 还是 amount_mismatch）
cd /opt/blcloud
node -e "
const D=require('better-sqlite3');const d=new D('data/app.db',{readonly:true});
console.log(JSON.stringify(d.prepare('SELECT order_no,channel,trade_no,amount,status,created_at FROM payments ORDER BY id DESC LIMIT 10').all(),null,1));
"
```

如果 payments 里**根本没有这条订单的记录**，说明微信的回调压根没打到服务器 —— 查回调域名和 nginx。
如果有记录但 status 是 `amount_mismatch`，说明金额被改了（几乎不可能，除非测试时改了商品价格）。

### 3.5 已付款但回调失败的兜底（补单）

微信的回调重试次数是有限的，一旦耗尽就再也不会通知。用户付了钱、订单却永远停在 `pending`，
系统提供两道兜底：

1. **用户自助**：用户打开「我的订单」时，系统会自动向微信查一次单（同一订单 60 秒内只查一次），
   确认已付就立即标记已支付并自动发货。
2. **管理员手工**：后台 → 交易管理 → 订单 → pending 订单点「向微信查单」。
   微信侧确认 `SUCCESS` 且金额一致才发货，不一致会拒绝并提示。

> 补单不能替代修好回调。回调连续报「无可用的平台证书 / RESOURCE_NOT_EXISTS」时，
> 真正的解法是去商户平台申请「微信支付公钥」并填到后台（见 3.1）。

## 四、blcloud 物联

### 4.1 后台自检

后台 → **系统设置 → 接入配置 → blcloud 物联平台** → 点「测试连接」。

成功会显示「连接成功：xxx@xxx」（即那个管理员账号的邮箱）。这一步不只是验管理员登录，
还会把开通流程的前置步骤都跑一遍（读租户信息 → 准备 Customer），哪一步挂了就直接报在哪一步。

> 注意：ThingsBoard 的 `POST /api/user` 只是**建档**，不带密码，平台也没有给管理员设密码的接口；
> 密码只能靠激活流程写入（取激活链接里的 `activateToken` → `POST /api/noauth/activate`）。
> 所以「用户已创建」不等于「账户能登录」。

### 4.2 自动开通是否生效

让一个**新**的微信号扫码登录（老用户在配之前就登录过，不会触发自动开通），然后：

```bash
cd /opt/blcloud
node -e "
const D=require('better-sqlite3');const d=new D('data/app.db',{readonly:true});
console.log(JSON.stringify(d.prepare('SELECT openid,nickname,tb_username,tb_status,tb_message FROM users ORDER BY id DESC LIMIT 5').all(),null,1));
"
```

期望 `tb_status` 是 `active`（不是 `pending` / `error`），`tb_username` 形如 `oXXXX@你的后缀`。

不是 `active` 时，看同一行的 **`tb_message`**：开通失败会写清卡在哪一步
（开关未开 / 管理员登录失败 / 准备客户失败 / 创建用户失败 / 激活账户失败 …）。
更完整的看后台 **接入配置 → blcloud 物联 → 「开通诊断」**：里面列出各状态的账户数量、
每个未开通账户最近一次的结果，以及最近 30 条开通步骤流水。

常见原因对照：

| tb_message | 原因 | 处理 |
|---|---|---|
| 未启用（开关没打开） | 「启用」开关没开，扫码登录时压根不触发开通 | 打开开关并保存 |
| 管理员登录失败 | 平台地址或管理员账号/密码不对 | 改完保存会作废旧令牌，立刻生效 |
| 准备客户失败 | 建不出 Customer（多为权限不足） | 换 TENANT_ADMIN 账号，或确认默认客户名 |
| 创建用户失败 | 建档被拒，看冒号后面的原文 | 通常是邮箱后缀冲突或权限不足 |
| 激活账户失败 | 拿不到激活链接，或密码不符合 TB 密码策略 | 检查密码策略（默认 ≥6 位）；系统会自动换强密码重试一次 |

历史账户（开关打开之前就注册过的）不会自动补开，两种方式：
让用户**重新扫码登录一次**（现在登录时会自动补开），或管理员到
**用户管理 → 详情 → 开通/同步 blcloud 账户** 手工点一次。

### 4.3 API 密钥走一遍

用户端登录 → 个人中心的 blcloud 板块 → 生成 API 密钥（形如 `blc_xxx`）→ 然后服务器上验证：

```bash
KEY="blc_粘贴你的密钥"
B=https://www.bliot.cn/platform

# ① 换访问令牌
TOKEN=$(curl -s -X POST "$B/api/blcloud/v1/token" \
  -H "X-Api-Key: $KEY" | node -e "let s='';process.stdin.on('data',d=>s+=d).on('end',()=>console.log(JSON.parse(s).access_token||''))")
echo "token: ${TOKEN:0:20}..."

# ② 看自己
curl -s "$B/api/blcloud/v1/me" -H "Authorization: Bearer $TOKEN"

# ③ 看可用接口清单
curl -s "$B/api/blcloud/v1/_endpoints"

# ④ 看额度消耗记录
curl -s "$B/api/blcloud/v1/usage" -H "Authorization: Bearer $TOKEN"
```

`_endpoints` 返回的是路径白名单 —— 只有在白名单里的路径才能被代理，这是防滥用的闸门。

## 五、端到端：完整走一遍业务

按顺序做一遍，模拟一个真实客户：

1. 后台建档产品 → 填价格、上传安装包、上架到官方商城
2. 后台生成授权码（或用售价让客户自己买）
3. 微信扫码登录用户端 → 商城下单 → 微信支付 0.01 元
4. 支付成功 → 授权自动发放
5. 用软件端 API 拿这个授权码去激活（`/api/open/v1/license/activate` 之类，见 `docs/软件端接入API.md`）
6. 后台查看：订单、授权、积分、统计四个地方都对得上
