## A. 定时换票接口

### A1. 唯一 path：`POST /license/ticket`（已上线可用）

- 服务端实现：`server/routes/open.js` → `app.post('/api/open/v1/license/ticket')`。
- 完整地址：`https://www.bliot.cn/platform/api/open/v1/license/ticket`。
- 《软件端接入API.md》接口总表（第 203 行）与 §5.6（第 555 行）均记作
  `/license/ticket`，文档与服务端一致，**无需再改**；请贵方方案 §4.5 把
  `/auth/ticket` 更正为 `/license/ticket`。

### A2. 鉴权与请求体

- **必须带 `Authorization: Bearer <access_token>`**：换票走用户会话守卫
  （requireClient），不是应用级公开接口。
- `machine_code`：**规则上是必填，实现上有兜底** —— 取 `body.machine_code`
  （兼容 machine_id / machine），为空时回退会话里的 `machine_id`；两者都无
  才回 `400 MACHINE_REQUIRED`。会话由激活时绑定机器，正常客户端 body 带上
  即可。
- `build_hash`：**选填**（≤64 字符，仅入票与台账，不参与匹配）。

### A3. 签票密钥：第三把独立 Ed25519（offline），kid = `b40170db9b699ece`

- 签票用的是 **离线票据专用密钥**（`data/offline-signing-key.json`，与
  manifest / entitlement 两把互相独立），不是契约 §5.6 示例里的
  `9f3a1c7b2d40e851` —— 那只是文档格式示意值（已在 §5.6 补注释说明）。
- **实际 kid 以你方已实测的 `GET /app/keys` 响应 `offline.kid` 为准，即
  `b40170db9b699ece`**；对应 PEM 取同一响应的 `offline.public_key`
  （SPKI PEM）。我方不在书面答复里转抄 PEM，避免转写出错 —— 公钥构建期内嵌
  请直接以 /app/keys 为唯一事实源。
- 票响应里的 `public_key` **恒等于** `/app/keys` 的 `offline.public_key`
  （同一把密钥、同一次加载）。

### A4. `machine_id` 与 `machine_code` 恒等

服务端在票 payload 里把两个字段写成**同一个字符串**（`machine_code` 为准，
`machine_id` 仅兼容老客户端字段的别名）。验签步骤用哪个字段、硬规则用哪个
字段，结果都一样；贵方以 `machine_code` 为准即可。

### A5. 四硬规则与异常行为确认（逐条对源码核实）

| 规则 | 服务端行为 | 确认 |
|---|---|---|
| seq 严格大于本地最大 | 按 `(license_id, machine_code)` 单调 +1，落 `license_ticket_seq`；客户端收到 seq ≤ 本地最大 = 重放，直接拒 | ✅ |
| epoch 变即整批作废 | 停票时 `epoch = epoch + 1` 且置 `stopped_at`；恢复只清 `stopped_at`/`stop_reason`，**seq 不归 1、epoch 不再变动**。所以恢复后新票 epoch = 停票后的新值、seq 继续递增，客户端「epoch 变 → 整批作废」规则完全成立 | ✅ |
| machine_code 必须本机 | 与会话 machine_id 不一致 → `403 MACHINE_MISMATCH`；两处都没有 → `400 MACHINE_REQUIRED` | ✅ |
| 宽限用票内 iat | `exp = iat + offline_days`（再与授权 `end_at` 取小）；宽限从签发时刻起算 | ✅ |
| 停票 403 | 停票后下次换票回 `403 TICKET_STOPPED`（带 reason / stopped_at） | ✅ |
| refresh_in 不 cap offline_days | TTL 只是「建议下次换票间隔」（`refresh_in = min(exp, iat+TTL) − iat`，下限 60s）；离线可用时长只由 `offline_days` 决定 | ✅ |

## B. 票据 TTL 与离线换证周期

### B1. 数值

| 项 | 值 |
|---|---|
| `ticket_ttl_hours`（服务端设置项） | **24**（代码默认 24；后台设置项，T0 前我方核查一次生产无覆盖值，随 SKU 定稿回执一并确认） |
| `expires_in` | **非固定值** = `exp − iat`（秒），即 `min(iat + offline_days×86400, 授权 end_at)`；仅当 `offline_days=0` 时才与会话过期取小 |
| `refresh_in` | `min(exp, iat + ticket_ttl_hours×3600) − iat`（秒，下限 60） |
| payload `iat` / `exp` | **UTC 秒**（`Math.floor(Date.now()/1000)`）；`expires_in` / `refresh_in` / `server_time` 为秒 / ISO 字符串 |

### B2. offline_days 当前值

- 有档位（套餐）授权：走 **档位的 `plans.offline_days`**；无档位的历史授权/
  卡密池码：回退 **开放应用的「离线宽限」`open_apps.offline_days`**。
- 代码硬约束：`online_required=1` 的档位 `offline_days ≤ 7`（后台保存即校验）。
- 3+2 各 SKU 的最终值 **暂未定稿**（与 E1 同一批落库），计划 **T0（首个正式
  发售版本）前完成后台配置并出补充回执**；我方建议口径：在线档统一 3 天、
  离线档 30 天起（最终以定价定稿为准）。

### B3. LabelGo-Offline

- 换证周期：`refresh_in`（默认 24h 节拍）在联网时执行；断网可用时长由其
  档位 `offline_days` 决定（见 B2，未定稿）。
- 用量额度：断网期间按**票内 `limits`** 限额（`limits` 已进签名 payload）。
- seq 规则：与在线版同一套（A5），不区分 SKU。

## C. entitlement_sig 全量下发与转强制

### C1. 带 `entitlement_sig` / `entitlement_kid` 的接口全清单

服务端只要返回 license 内容就带签名（`licensePayload()` 统一签发，顶层或
license 对象内）：

| 接口 | 位置 |
|---|---|
| `POST /auth/activate`（激活） | `license.entitlement_sig` |
| 扫码登录 / 登录类响应 | `license.entitlement_sig` |
| `POST /auth/refresh` | `license.entitlement_sig` |
| `GET /user/licenses` | 列表每项都带 |
| `POST /license/verify` | **顶层 + license 对象内** 各一份 |
| `POST /license/heartbeat` | **顶层 + license 对象内** 各一份 |
| `POST /license/bind`（绑定卡密） | `license.entitlement_sig` |
| `POST /license/unbind` | `license.entitlement_sig` |
| `POST /license/ticket` | **顶层** `entitlement_sig`（随票实时签） |

签发时机：每次响应**实时对当前权益快照签名**，不是落库预签 —— 所以不存在
「改了档位但签名没跟上」的窗口。

### C2. canonical 与公钥（2026-11-12 修订：消除上版两句话的歧义）

**结论一句话：签的是「带 kid 的 entitlement」，不是「裸 entitlement」；`signature`
不参与签名，`kid` 参与签名。**

被签对象精确定义（服务端 `signkey.signObject(obj)` 的实际行为）：

```
signed = { ...entitlement }            // 先剔除 entitlement 里可能存在的 signature / kid
signed.kid = entitlement_kid           // 再强制注入 kid（覆盖任何同名键）
canonical = 键字典序排序 + 紧凑分隔符 + 数组保序 + UTF-8（中文不转义）
signature = base64(Ed25519(canonical))
响应中的 entitlement_sig = signature
```

- 「剔除 `signature`/`kid`」说的是**准备被签对象的步骤**（`signature` 是产出物，
  不能自己签自己；如果调用方在对象里塞了 `kid` 也先清掉）；
- 「kid 放进被签内容」说的是**最终被签对象里必须有 kid**（注入后）。
- 两句话是同一个流程的前后两步，不是两种口径 —— 上版写法确实容易误读，以本节为准。
- 客户端实现等价写法：`body = { ...entitlement }; delete body.signature; body.kid = entitlement_kid;`
  再对 `canonical(body)` 的 UTF-8 字节做 Ed25519 验签。
- canonical 规则与清单签名同一套；公钥固定 **`ent-2026-11`**
  （`data/entitlement-signing-key.json`，/app/keys `entitlement` 项）。
- **golden vector（可复现，含完整响应片段 + canonical UTF-8 + sha256 + 签名）已写入
  《软件端接入API.md》§5.6「权益签名 golden vector（v1）」**：两组样本
  （在线付费档 / 无档位历史码），key 为 `ent-vector-1` 测试密钥，生成脚本
  `tools/gen-entitlement-vector.js`。向量 A 的
  `sha256 = 50d05821e9e4d86219e3c515f7b0f9d612619df7643c799224622512b5e08b3b`，
  用向量公钥验签应 PASS；贵方按它对齐 canonical 即可完成跨端验证（四个易错点：
  键字典序、中文不转义、数组保序、`null`/空容器原样保留）。

### C3. 全量上线与转强制

- **已经是全量**：所有返回 license 的接口（上表 9 处）自 2026-11-11 部署起
  100% 携带签名，无灰度、无开关 —— 服务端没有「关签名」的开关。
- 历史授权 / 卡密池码：服务端**响应时也会实时签**（签的是其 legacy 权益
  快照），不存在服务端给不出的情况；「无签名」只会出现在贵方客户端**本地
  旧测试快照**上。贵方「无签名放行、有签名必验、验不过按免费版」的软兼容
  策略保留即可。
- **转强制时间：T0（首个正式发售版本）即可强制**。理由：发售版客户端首启
  必然从服务端拿到带签名的新快照，历史无签名快照只存在于内部测试机，
  外部用户为 0、无兼容包袱。可观测兜底：如需观察期，建议
  「T0 + 30 天后本地快照无 `entitlement_kid` 一律按免费版」。

## F. 鉴权与关停口径

### F1. `/auth/refresh` 放行确认 ✅（比你方预期更宽松）

- 服务端 `/auth/refresh` **不走应用级鉴权守卫**：只凭 `body.refresh_token`
  换新令牌（校验会话状态与 refresh_expires_at）——**不需要 Bearer、不需要
  X-App-Key、不需要 x-nonce，也不受公开模式频控**。贵方 1.0.54 带不带任何
  应用头都放行。
- 公开模式口径（其余写接口适用）：
  - POST 类写请求必须带 `x-nonce` → 缺失 `401 NONCE_REQUIRED`；
  - nonce 重复 → `401 NONCE_REUSED`；
  - 频控：每 IP 300 次/分、每 app+IP 120 次/分 → `429 RATE_LIMITED`；
  - GET/HEAD 不要求 nonce。

### F2. HMAC 关停时间表 ✅（文档已按 T0 重写，见《软件端接入API.md》§2.2.2）

| 节点 | 时间 | 判据 |
|---|---|---|
| S1 | **T0 = 首个正式发售版本发布日** | 发售包通过验收、且是唯一对外可分发包；1.0.52/53 为内部测试包，不计入 |
| S2 | T0 + 7d | **`hmac_legacy` 连续 7 天为 0，从发售日起算**；关旧密钥后旧值回 `401 APP_SECRET_RETIRED`（可重开） |
| S3 | S2 + 30d | 代码层移除 `hmac_legacy` 分支 |

「新版覆盖 ≥95%」判据已作废（§2.2.2 明确写入原因）。另：文档建议 T0 前
后台做一次**轮换密钥**（非重置），把 1.0.52/53 里那个明文值降级为
`app_secret_prev` 身份，S2 关掉即彻底失效 —— 我方会照做。

### F3. 清单公钥 kid 轮换承诺（含签名字段形状定稿）

**字段形状先定死，避免贵方门禁炸在数组上：`signature` + `kid` 两个字段永久保留、
类型永远是字符串、永远是单签；新增的多签信息只放在独立的 `signatures[]` 数组里，
纯增量，不存在「把 signature 改成数组」的版本。**

轮换期间清单的样子（过渡期）：

```json
{
  "product": "LabelGo",
  "latest": "1.0.60",
  "kid": "manifest-2026-11",
  "signature": "<旧 kid 的 base64 签名>",
  "signatures": [
    { "kid": "manifest-2026-11", "signature": "<旧 kid 的 base64 签名>" },
    { "kid": "manifest-2027-05", "signature": "<新 kid 的 base64 签名>" }
  ]
}
```

- **过渡期内 `signature` / `kid` 始终是旧 kid**（只读单签的客户端零改动、零风险）；
  新 kid 只出现在 `signatures[]` 里。
- 切换点（新客户端覆盖到位后）才把 `signature` / `kid` 指到新 kid，`signatures[]`
  继续同时带旧 kid 一段时间；收尾时移除旧条目。
- canonical 会**同时剔除 `signature` 与 `signatures`**，再注入 `kid` —— 两个字段都
  不参与签名，`signatures[]` 不会自引用。
- 未进入轮换过渡期时，响应里**没有 `signatures` 字段**（不是空数组）。贵方门禁按
  「字段缺失即忽略」处理即可，今天无需任何改动。
- 客户端建议判据：先按 `kid` + `signature` 验；失败且 `signatures[]` 存在时遍历数组，
  用内嵌公钥表按 kid 选公钥。这样 P1 阶段不用改代码，P2 才需要认数组。

配套承诺（不变）：

1. **轮换前 ≥30 天书面通知**贵方，给出新旧 kid、切换日期、过渡期长度；
2. 过渡期 `/app/keys` 同时下发新旧两把清单公钥（`manifest` 与
   `manifest_prev`（或 `manifests[]`，届时随通知一并定形状，同样只增不改））；
3. 过渡期结束才停止旧 kid 签名；期间任何单 kid 变更都会提前回执。
4. 现状说明：当前服务端密钥仓为单 kid、单签；上述「双签 + signatures[]」是首次轮换前
   必须先落地的小改造，我方在收到轮换需求时先改造再轮换 —— 即「先有双签，后换 kid」，
   绝不裸切换。
